## 2. F1 — 批量充值地区选择

### 2.1 现状

- 地区（`payment_country`）是**发码时**确定的，兑换时从码继承。单张兑换本身也没有地区选项，这是对的。
- 发码页 `CDKeyManagement.vue:90-96` 有地区下拉，选项来自上游 `GET /admin/cardplatform/plans` 返回的 `payment_regions`（仅 spacexcard-legacy 协议支持；`provider/registry.go:10-13`）。
- **管理端批量充值**（`views/admin/BatchRechargeView.vue` + `handler/admin_batch_recharge.go`）是「为每个账号现发一张码再兑换」，但：
  - UI 无地区控件；`loadPlans()`（`:753-781`）拿到了 `payment_regions` 却丢弃；
  - 请求体 `batchRechargeCreateReq`（`:91-95`）无该字段；
  - `submitOneRecharge` 调 `cli.IssueCDKs(ctx, plan, 1, idem)`（`:829`）不带 `IssueCardPref` → **上游默认菲律宾**；同时也漏了站点选卡偏好 `issuePrefFromSite()`；
  - `SaveCardplatformCDKCodeForAccount`（`:848`）不写地区 → 码表显示「待同步」。
- git 历史确认：批量路径**从未加过**地区，不是被删。
- 代理批量（`partner/BatchView.vue`）和公开批量兑换（`user/BatchRedeemView.vue`）用的是已有的码，地区随码，不需要选择。

### 2.2 方案

**管理端批量充值：批次级地区，一个批次一个地区，不做逐行覆盖。**

后端（`handler/admin_batch_recharge.go`）
1. `batchRechargeCreateReq` 加 `PaymentCountry string \`json:"payment_country"\``，trim + 大写。
2. 非空时校验 `provider.SupportsPaymentCountry(primary.Protocol)`，不支持则 400（文案与 `cardplatform_cdk.go:251` 一致）。
3. `batchFingerprint` 纳入地区（避免同账号不同地区被误判为重复提交）。
4. `runBatchRecharge` → `submitOneRecharge` 透传地区；发码改为
   `cli.IssueCDKs(ctx, plan, 1, idem, mergePref(issuePrefFromSite(), IssueCardPref{PaymentCountry: pc}))`，与单张发码路径（`cardplatform_cdk.go:293-299`）一致。
5. `SaveCardplatformCDKCodeForAccount` 传入地区。
6. 审计日志带上地区；`AdminBatchRechargeRetry` 从持久化字段读取地区，保证重试一致。

数据库
- `admin_recharge_batches` 加列 `payment_country TEXT DEFAULT ''`，迁移沿用 `db/cdk_region.go:10-23` 的 `pragma_table_info` + `ALTER` 模式；`AdminRechargeBatch` 结构与列表/详情查询加字段。

前端（`views/admin/BatchRechargeView.vue`）
- 保存 `payment_regions`；在套餐选择旁加地区下拉（复用发码页的 `regionLabel` 与「默认（菲律宾）」空选项）；列表为空时隐藏。
- 请求体加 `payment_country`；确认弹窗与批次详情显示地区。
- i18n：`zh.ts` / `en.ts` 增加对应 key。

**代理批量：只展示，不可选。**
- `ValidateAgentCDKBatch`（`db/agent_cdk.go:393`）返回每张码的 `payment_country`；`partner/BatchView.vue` 显示地区，批次内混合多个地区时给出提示。
- `agent-openapi.yaml` 注明「付款地区由卡密决定」。

## 4. 安全加固

### S1（P0）查卡接口：限流 + 邮箱打码 + 去掉回源放大

现状（`handler/lookup.go`，路由 `server/http.go:197-203`）
- `/lookup/cdk`、`/lookup/cdk/batch`、`/lookup/task` 无任何限流。
- `account_email` 原样返回（`:288`、`:342`）；同文件 X 收件人已打码（`:162-166`），口径不一致。
- 每张有 `redemption_token` 的码都会实时调上游 `cli.Result`（`:323-325`），batch 一次最多 100 次上游调用。

方案
1. **通用限流组件** `handler/ratelimit_ip.go`：滑动窗口，按 key 计**权重**（batch 按码张数计），带后台清理（每分钟清过期 key）和 key 总数上限。替换现有 `xPublicAllowed`、`tgPublicAllowed`、`swapRateAllow` 三份重复实现。
2. 额度：见 §6「实际限流额度」。管理员登录态不受限、可见完整邮箱；超限返回 429 + `Retry-After`。
3. **邮箱打码**：本地部分只保留前 2 位和最后 1 位，中间替换为 `***`，域名完整保留（例：`jo***e@example.com`），单查和批量都打码。CSV 导出随之打码。
   - 买家自己核对账号仍然够用；完整邮箱只在管理端可见。
4. **批量不回源**：batch 路径只读本地库（`cd_keys` / `cardplatform_cdk_codes` / `recharge_tasks` / 绑定表），跳过 `cli.Result`；单查保留回源（已受限流保护）。webhook 和后台同步已在持续更新本地状态，批量查询读本地足够。

### S2（P1）代理换码竞态

现状（`handler/agent_exchange.go`）
- `:153` 先查「是否换过」，`:248` 发新码，`:276` 才写换码记录；表 `agent_cdk_exchanges` 无唯一约束；幂等键含 `UnixNano`（`:245`），上游也不去重。
- 并发 N 个请求 → 都通过检查 → 发出 N 张新码。
- 另外旧码在新码发出**之后**才禁用，禁用失败时新旧码同时可用。

方案
1. 迁移：清理历史重复（保留最早一条）后建 `UNIQUE INDEX idx_agent_ex_old_hash_uniq ON agent_cdk_exchanges(old_code_hash)`。
2. 流程改为「先占位，后发码」：
   - `INSERT ... (old_code_hash, status='pending')`，唯一冲突 → 409「该卡密正在或已经换过」；
   - **先禁用旧码**，失败则删占位并返回 502（旧码仍有效，用户可重试）；
   - 再发新码，幂等键固定为 `agent-swap-<codeHash>`（去掉时间戳，上游层面也去重）；
   - 成功后把占位更新为 `done` 并写入新码信息；发码失败把占位标记为 `failed` 并保留旧码禁用状态，交由管理员在后台处理（记审计）。
3. 表加 `status` 列。

### S3（P1）客户 session 明文永久落库，凭卡密即可被他人使用

现状
- `PublicCDKPreflight`（`cardplatform_cdk.go:1191-1195`）把 `credential.session` 写进 `cdk_session_bindings`，永不删除。
- `SessionBillingCheck`（`gpt_billing.go:158-181`）只给卡密时，会取出**客户的 session** 去查订阅和发票（Stripe 发票含姓名、地址、卡号后四位）；代理码甚至凭邮箱直接给 accounthub 发票链接（`:166`）。
- 卖码的代理、或通过查卡接口拿到码的人，都能看到买家账单；数据库/备份泄露 = 所有客户 ChatGPT 账号被接管。

方案（已按「保留凭卡密查账单」的决定调整）
1. **加密存储**：`cdk_session_bindings.session_payload` 与 `admin_recharge_items.gpt_password / email_password / session` 写入前 AES-GCM 加密（`db/secretbox.go`，前缀 `enc:v1:`），读取时解密；兼容未加密的旧值。
2. **存量迁移**：启动时把明文行逐行加密（幂等，已加密的跳过）。
3. **密钥**：`SECRET_ENC_KEY`，未设置时由 `JWT_SECRET` 派生。**密钥一旦更换，旧密文解不开**（读取返回空，等同没有绑定：凭卡密查账单、批量导出凭据会失效）。
4. 账单查询仍可仅凭卡密，但已加 10 次/分钟/IP 限流（S1）。

> 残余风险：拿到卡密的人仍可查该账号账单。这是保留「凭卡密查账单」的代价；加密只防数据库/备份泄露。

### S4（P2）preflight 无鉴权写入/覆盖绑定

现状：`cardplatform_cdk.go:1180-1196` 即使上游返回错误、即使 code 不存在也会写入，`ON CONFLICT DO UPDATE` 可覆盖他人绑定。

方案：仅在上游 2xx、code 在本地存在、且 token 与该 code 已绑定的 token 一致时才写；有效载荷限制在 16KB（配合 S3 后只存邮箱，问题基本消失）。

### S5（P2）内存与请求体

- `handler/ratelimit.go:107-121`：登录限流 key = `IP|用户名`，失败数 <5 的条目永不删除，用户名长度不限 → 用长随机用户名可打爆内存。修：用户名截断到 64 字符再做 key；统一改用 S1 的带清理限流组件。
- 全局加 `http.MaxBytesReader` 中间件：默认 1MB（批量接口 4MB）。
- Caddy 加 `request_body { max_size 4MB }`。

### S6（P2）敏感值进访问日志

`gin.Default()`（`http.go:40`）记录完整 query：`/public/cdk/result?token=`、`/result-by-code?code=`、`/lookup/cdk?code=`、`/setup/bootstrap?setup_token=`。能看日志的人可以收集未用卡密。

方案：改 `gin.New()` + `gin.Recovery()` + 自定义日志中间件，只记录 path 不记录 query；删掉 `setup_token` 的 query 兜底（`setup.go:105`），只接受 header。

### S7（P2）弱 JWT 密钥

`deploy/app.env.example:6` 的 `change-me-to-random-32chars-min` 能通过 `enforceJWTSecret`（`http.go:77-80`）。照抄示例的部署，任何人都能用公开字符串签发管理员 token。

方案：拒绝包含 `change-me` / `your-secret` / `dev-secret` 的值；最小长度提到 32；`auth.go:20` 的硬编码兜底密钥删除（非 release 模式下随机生成并打印警告）。**上线前请确认生产 `JWT_SECRET` 不是示例值。**

### S8（P2）反代真实 IP 配置

现状
- Docker：`TRUSTED_PROXIES=172.16.0.0/12` 依赖 Docker 恰好分配 172.x 网段；`Dockerfile` 默认值信任整个 172.16/12。
- systemd：`TRUSTED_PROXIES=127.0.0.1` 正确，**前提是 Cloudflare 不是橙云代理**。若开了橙云，Caddy 看到的是 CF 边缘 IP，`deploy/Caddyfile.snippet` 里 `header_up CF-Connecting-IP {client_ip}` 还会把真实值覆盖掉。
- 后果：全站共用少数几个 IP → 任何人输错 5 次管理员密码即可让真管理员被锁 15 分钟（可无限重复）；S1 的新限流也会变成全站共享额度。
- `SetTrustedProxies` 的返回错误被忽略（`http.go:45`）。

已实施（Docker + 橙云）
- `Caddyfile` 与 `deploy/docker-deploy.sh` 生成的 Caddyfile：全局 `servers { trusted_proxies static <CF IP 段>; client_ip_headers CF-Connecting-IP }`，Caddy 的 `{client_ip}` 即访客真实 IP，并写入 `X-Real-IP`。
- 应用 `RemoteIPHeaders` 优先 `X-Real-IP`（`X-Forwarded-For` 末尾是 CF 边缘 IP，从右取会取错）。
- `docker-compose.yml` / `Dockerfile`：`TRUSTED_PROXIES` 覆盖三段私网（应用端口不对外发布，只有 Caddy 能直连）。
- `deploy/Caddyfile.snippet`（systemd 方案）不再用 `{client_ip}` 覆盖 `CF-Connecting-IP`。
- `SetTrustedProxies` 出错时启动失败。
- **上线须同步更新服务器上的 Caddyfile**：`docker-deploy.sh` 只在首次部署时生成它，已有部署要手工把全局块加进去并 `docker compose restart caddy`。

### S9（P2）JWT 不可吊销 — 下一期

代理 JWT 路径不复查代理状态（`middleware.go:186-212`），管理员中间件不查 `is_active`，改密不失效旧 token，token 还在 JSON 里返回并存 localStorage。建议下一期做 `token_version` 方案。本期只做最小修补：中间件里补查代理 `status` 和管理员 `is_active`（每请求一次主键查询，代价可接受）。

### S10（P3）Webhook / 易支付

- `webhook.go:81` 只对 `X-Avanfinity-Webhook-Timestamp` 做时间偏差校验，其他时间戳头和无法解析的时间戳都放行。修：对实际参与验签的时间戳做 ±5 分钟校验，无法解析即拒绝；副作用按事件 id 去重。
- `epay/epay.go:136` 验签改 `hmac.Equal`；`:140` 空 `trade_status` 不再视为成功。

### S11（P3）错误透传

`writeCardErr`（`cardplatform_cdk.go:67`）及公开 preview/preflight/redeem/result 直接返回 `err.Error()`，会带出上游 URL/IP。修：对外统一「上游服务暂时不可用，请稍后重试」，详细错误写日志并附 request id。

### 已检查无问题（备查）

Setup token 哈希存储 + 常量时间比较；代理 webhook 的 SSRF 防护（连接时校验 IP、不跟随重定向）；静态文件路径穿越；SQL 均参数化；CORS 白名单 + CSRF 双提交；bcrypt / API Key 哈希；自更新 sha256 校验。

### 上线清单

1. **备份数据库**（加密迁移会改写 `cdk_session_bindings`、`admin_recharge_items`；换码表会加唯一索引）。
2. **更新服务器 Caddyfile**（加 Cloudflare 全局块）并重启 Caddy。不做这步，所有访客会被识别成少数几个 CF 边缘 IP，全站共用限流额度。
3. 确认 `.env` 里的 `JWT_SECRET` 不是示例值（否则新版本拒绝启动）。`docker-deploy.sh` 生成的是 64 位随机值，正常没问题。
4. 建议在 `.env` 显式设置 `SECRET_ENC_KEY`（`openssl rand -hex 32`），并与 `JWT_SECRET` 一起长期保存。**之后不要再改**，否则已加密的 session 解不开。
5. 上线后验证：
   - 用手机网络访问 `/api/v1/lookup/cdk?code=…` 连续 31 次，第 31 次应返回 429
   - 日志 `[GIN]` 行的 IP 应为访客真实 IP，不是 `172.x` 或 CF 段
   - 查卡结果里的邮箱已打码；管理员登录后可见完整邮箱
   - 管理端「批量充值」能看到并选择付款地区
   - 启动日志若出现「发现 N 条重复换码记录」，说明历史上已经被并发换出过多张码，需要对账
6. 回滚：直接回滚镜像即可；已加密的数据旧版本读不了（旧版本会把密文当 session 原样使用，凭卡密查账单失败），所以回滚后这一功能不可用，兑换主流程不受影响。
