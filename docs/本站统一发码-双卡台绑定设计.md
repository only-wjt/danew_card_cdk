# 本站统一发码 · 双卡台预绑定设计

> 日期：2026-08-27　·　版本：1.0　·　状态：**待确认后实现**（本文只定设计，不改代码）  
> 产品决策来源：站长明确要求「本站统一对外发码；生成后立刻向 A、B 各申请一张；兑换按规则路由；A 挂了自动切 B」。  
> 本文取代旧文里「新发码只选一台、兑换永不换台」对 **新本站码** 的适用。旧文仍适用于 **legacy 原生码**。

对照：

| 文档 | 还管什么 |
| --- | --- |
| `docs/多卡台接入设计.md` / `docs/多卡台接入方案.md` | 两套协议差异、adapter、账户表、legacy 前缀路由。其中「兑换绝不换台」**只约束 GPTD-/SXC-/AVF- 原生码** |
| `docs/代理购卡库存同步-对接说明.md` | 二级拉单 + `order.delivered`。多卡台落地后 `issued_codes` 改为 **本站码**，契约形状不变 |
| `backend/internal/cardplatform` | 现网单账户透传：`X-API-Key` + `upstream_id INTEGER` + 用户码原样转发 |
| `backend/internal/db/local_stock.go` | GPT 白号本地库存，**不走双绑** |

## 0. 一句话

**对外只发本站码。每张新本站码在生成当下预购 A 码 + B 码并绑死。用户/代理始终只拿本站码。兑换先打 A，A 不可达再拿 B 的原生码去兑 B。已经发出的 GPTD-/SXC- 等原生码继续只在原发卡台兑，不补绑、不切台。**

这和现网、和此前两版设计都不同：

| 方案 | 用户手里的码 | 上游码何时买 | 兑换切台 |
| --- | --- | --- | --- |
| 现网生产 | 卡台原生码（`GPTD-` / `SXC-`） | 发码时买一台 | 否，原样转发 |
| 旧设计（协议升级） | 仍是某台原生码 | 发码按优先级选一台 | **否**（码已绑死协议） |
| 旧想法（兑时选台） | 本站码 | 兑时从池里取一台 | 兑时选，不预购两张 |
| **本稿（目标）** | **本站码 `DN-`** | **发码时 A+B 各买一张** | **仅新本站码：A 挂了用 B** |

## 1. 必须先确认的产品决策

实现前请站长拍板这四条。正文按「推荐默认」写死，改默认会动表状态机。

| # | 决策 | 推荐默认 | 为什么 |
| --- | --- | --- | --- |
| D1 | **2× 上游成本谁付** | 站内消化：代理人民币价仍是一张本站码的价，**不向代理收两次**。注意 2× 是**资金占用**不是净亏：未用的那张按 D2 删除退款后，净成本 ≈ 1× + 不可退部分。管理发码页展示「将同时购 A+B，履约后退回未用的一张」 | 代理/用户只看到一张码；收两次会把分销价打穿，也和「统一发码」矛盾 |
| D2 | **A 兑成功后未用的 B** | **删除并退款**优先：调对应协议的删除接口（旧台 `DELETE /cdks/{id}`，购买所得会**自动退回已付服务费**），本站标 `refunded`。删除失败或协议不支持退款 → 退化为 disable，标 `retired` | 继续留着 = 泄漏面 + 长期占上游库存；A 已履约后再兑 B = 双开卡。旧台明确支持「删除即退服务费」，只 disable 等于白扔一张的钱 |
| D3 | **只做成 A、B 失败一半** | **主路径失败整张本站码**（不激活、不交给代理）。A 已买到则重试 B 2 次，仍失败则尽量 disable A。站点开关 `allow_degraded_single_bind` **默认关**，打开才允许「只有 A、无兜底」降级出货 | 付 2× 就是为了保证能切 B；默许 A-only 等于卖了不能切台的码 |
| D4 | **代理名下的本站码能否上公开兑换页** | **能。** `DN-` 不受现网 `block_public_redeem` 拦截。旧原生码维持现网默认拦截 | 「同一张本站码给普通用户和代理用」是本方案硬要求；代理是分销，终端用户贴到公开页兑换 |

其余已定、不另问：旧码不回填双绑；白号不双绑；`credit*` 不进新台 generate；永不把 A/B 原生码给代理/用户/二级 webhook。

## 2. 角色与他们看见什么

| 角色 | 入口 | 看见 | 看不见 |
| --- | --- | --- | --- |
| 站长 | `/ops/integration`、`/ops/cdkeys`、代理管理 | 账户 A/B、健康/熔断、本站码、绑定摘要（A✓ B✓）、履约台、上游码（仅「查看上游绑定」折叠） | — |
| 普通用户 | 公开兑换页 `/`、账单查询 | 输入框、套餐结果、进度。占位符改为「粘贴卡密」 | 卡台名、A/B、是否发生过切台 |
| 一级代理 | 门户购卡 / 我的卡密 / 订单 | 本站码、套餐、状态、复制。易支付付一张的钱 | 上游码、双倍成本明细、卡台名 |
| 二级 / Agent API | `GET /agent/orders`、`GET /agent/cdks`、`order.delivered` | `issued_codes` = **本站码数组** | 绑定表、远程码、`remote_id` |
| 运营告警 | 站内横幅 + 审计日志 | 「B 发码失败，本批未出货」或降级开关打开时的 A-only | 完整上游码（日志打 prefix + remote_id） |

**原则：本站码是唯一对外身份。** A 码、B 码是履约零件，和卡台 API Key 同一保密级别。

## 3. SKU 与范围

### 3.1 走双绑的（目标模型）

逻辑套餐 key 与现网一致，且 **A、B 两台都能 generate** 的档：

- `go` / `plus` / `pro_5x` / `pro_20x`（以当时两边 `SellablePlans` 交集为准）

发一张本站码 = 向 A `Issue(plan, 1)` + 向 B `Issue(plan, 1)`。管理端点一次「购买 N 张」= N 张本站码 = 2N 次上游发码。

### 3.2 不走双绑

| SKU | 原因 | 对外码 | 兑换 |
| --- | --- | --- | --- |
| **GPT 白号** `gpt_white` | `local_stock`，站长导入，无卡台 | 导入的原始串；`code_kind=local_stock` | 本站本地履约，不打 A/B |
| **`credit*`**（credit250/500/1000） | 新 Avanfinity `generate` / `cdk-offers` **没有**点数档；旧台才有 | 见 §3.3 | 只打旧台，**禁止 failover** |
| **已发出的 GPTD-/SXC-/AVF-** | 历史透传，码本身就是上游码 | 原码，无 binding 行 | 只打原发卡台 |

白号继续用负 `upstream_id` 挤在 `cardplatform_cdk_codes`，不要和本站码、绑定表搅在一起。实现时看到 `plan=gpt_white` 或 `code_kind=local_stock` 直接走 `PlanFulfillment=local_stock`。

### 3.3 credit* 怎么发（避免和双绑混）

- **不**向新台 `POST /gpt-direct/cdks/generate`。
- **不**做 A+B 预购。
- 推荐对外仍发 **本站码 `DN-`**（用户体验统一），但 `dual_eligible=0`，只有 **一条** binding，指向旧台账户。
- 管理列表徽章：`单绑 · 无兜底`。
- 若旧台当时不可用：整单失败，不要「先发本站码再补绑定」。

备选（不推荐）：credit* 继续发 GPTD-/SXC- 原生码。缺点是用户/代理要同时认两套前缀。

## 4. 定价、余额、配额

### 4.1 钱怎么算

| 层 | 规则 |
| --- | --- |
| 上游 A | 旧协议：发码扣套餐服务费。新协议：generate **不扣**套餐费，`forceNewCard` 开卡费由生成者承担 |
| 上游 B | 同上，按 B 的协议各算各的 |
| 本站对代理 | `agent_plan_fees` 人民币价 **按 1 张本站码**。禁止「数量 × 2」或拆成两个 SKU |
| 本站对管理发码 | 按钮文案写清「同时向 A、B 各购 1 张」；估算金额 = A 成本 + B 成本（两套报价，旧台用服务费、新台用 `salePrice`） |
| 对用户 | 用户不付钱给本站（公开兑换是核销） |

**推荐：2× 成本写进站长毛利，不要转嫁代理。** 若毛利盖不住，上调 `agent_plan_fees`，仍然是「一张本站码一个价」。

### 4.2 发码前预检

两边都要过，缺一则 **不创建** 本站码（连 `pending` 都不对外）：

1. 账户 `status=active` 且熔断未开。
2. 该账户 `SellablePlans` 含此 plan。
3. 新台：`pricingStatus=READY && salePrice != null && stock>0`（stock 未知则只做软警告，不挡）。
4. 旧台：有 API Key、Ping 最近成功（或本次预检 Balance 不报 5xx）。
5. 余额：旧台 `spendable_balance` 够 1 张服务费；新台按 adapter 声明的「生成是否要余额」检查。不够 → 整单失败，文案「A 余额不足」或「B 无库存」，不要静默改成单绑。

代理购卡：预检失败 → 订单 `paid_undelivered`，推 `order.fulfill_failed`，`issued_codes=[]`。站长可重试，重试走完整双发，不沿用半成品。

### 4.3 部分发码（D3 展开）

对 **一张** 本站码：

```
预检两边 OK
  → 写本站行 issue_status=pending（不出现在可复制库存）
  → Issue A（幂等键见 §12）
      失败且不可恢复 → 删/作废 pending 行，整张失败
      成功 → 写 binding A（unused）
  → Issue B（独立幂等键）
      超时 → 同键重放（≤2 分钟窗口）
      仍失败 → 再换键重试 1 次
      仍失败 → 【主路径】尽量 Disable A，binding A=failed，本站行 issue_status=failed，不划给代理
              → 【仅当 allow_degraded_single_bind=1】激活本站码，dual_eligible=0，打告警「A-only 降级」
  → 两边都 unused → issue_status=active，status=unused，可划拨/可复制
```

批量（管理 N 张、代理 count=N）：**按张原子**。第 3 张双发失败不影响已激活的 1、2 张。代理订单：已激活的本站码写入 `issued_codes`，未齐则 `paid_undelivered`（与现网 `FailAgentOrderDelivery` 一致）。不要把「A 成功 B 失败」的 pending 行发给代理。

## 5. 旧码（legacy）——必须继续能用

### 5.1 识别

满足任一即 legacy，**禁止**走双绑路由：

- `code` 前缀 `GPTD-` / `SXC-` / `AVF-`（大小写不敏感）
- 或 `cardplatform_cdk_codes.code_kind='legacy'`
- 或该行在 `site_cdk_bindings` 中 **0 行**

`AVF-` 若将来从新台直接发出（未包本站码的过渡），仍按旧设计：前缀选 Avanfinity 账户，**不 failover**。

### 5.2 行为（保持现网语义）

- 公开兑换：用户码 **原样** 转发给原账户的 Preview/Preflight/Redeem。
- 查询 / 禁用 / webhook：按 `upstream_id` 或 `(provider, remote_id)` 回写，不换台。
- 不回填 binding，不把旧码改写成 `DN-`。
- `block_public_redeem` 对 legacy **继续生效**（现网默认开：已分配代理的原生码不能上公开页）。

### 5.3 代理换码（`/partner/swap`）

- 旧码换出：走现网逻辑（未扣款失败 → 旧台再发 1 张原生码）。
- 本站码换出：作废本站码 + disable 两条还 unused 的 binding，再 **双发一张新本站码**。返回给代理的是新 `DN-`，不是上游码。
- `agent_cdk_exchanges` 增 `old_site_code` / `new_site_code`；旧的 `old_upstream_id` 仅服务 legacy。

## 6. 代理与公开兑换（同一张本站码）

### 6.1 代理购卡（与现网同形，码变了）

```
一级代理选 plus × N → 易支付
  → paid → fulfillAgentOrder
  → 循环 N 次 DualIssue（每张 DN- = A码+B码）
  → AssignCDKsToAgent(本站码)
  → CompleteAgentOrderDelivery(issued_codes=[DN-...])
  → enqueue order.delivered（issued_codes 只有本站码）
  → 门户「我的卡密」/ 二级拉单入库
```

现网 `issueCDKsForAgentOrder` 一次向上游要 N 张；双绑后改为 **N 次 DualIssue**（每次上游 count=1+1）。幂等键按「订单 + 序号 + 账户」拆开，避免一张失败导致整批重放错位。

### 6.2 站长划拨 / 收回

`AssignCDKsToAgent` / `UnassignCDKsFromAgent` 继续按 **本站码字符串** 匹配 `cardplatform_cdk_codes.code`。不要按 `upstream_id` 当主键（本站码没有可信的卡台整数 id）。实现时把 `UPDATE ... WHERE upstream_id=?` 改成 `WHERE code=?`（或新列 `id`）。

划拨的是本站行；binding 跟着走，不单独划。

### 6.3 二级 / Agent API

- `GET /agent/orders`、`GET /agent/cdks`、`order.delivered`：`code` / `issued_codes` = `DN-…`
- 入库主键仍是 `order_no`，不要用卡密当订单主键（对接文档已如此）
- 二级把 `DN-` 发给自己的客户 → 客户到 **本站公开兑换页** 粘贴即可
- 代理批量充值 API：请求体里的 cdk 也是本站码；服务端换成 binding 的 `remote_code` 再调上游 Redeem
- **禁止**在任何 agent webhook（`recharge.*` / `order.*`）里带 `remote_code`、`remote_id`、账户名

### 6.4 公开兑换（UX 不变）

用户粘贴本站码 → Preview / Preflight / Redeem / Result。  
BFF **不得**把 `DN-` 转给卡台。替换规则见 §11。

若发生 A→B 切换：响应里不出现「已切换至 B」。进度、token、账单绑定一律挂在 **本站码** 上（`cdk_session_bindings.cdk_code = DN-…`）。

### 6.5 与 `block_public_redeem` 的冲突（D4）

现网 `guardAgentAssignedCDK`：已分配代理的码，公开页默认 403（`CDK_AGENT_CHANNEL`）。这和「代理买了交给客户自己兑」打架。

| 码 | 公开页 |
| --- | --- |
| `DN-` 本站码 | **放行**（即使 `assigned_agent_user_id>0`） |
| legacy 原生码 | 维持现网策略 |
| 白号 | 不走公开卡台兑换 |

并发双兑靠本站行锁（§13），不再靠「禁止客户兑」来防重复。

代理渠道自己已经 `reserved`/`consumed` 的本站码：公开页 Preview 返回「已在充值/已使用，可查进度」，与现网文案类似，但 **不要**再说「请联系购买方代为充值」。

## 7. 「A 挂了切 B」——精确定义

只发生在 **新本站码的兑换/重试**，不发生在发码选台（发码是两边都买），也不发生在 legacy。

### 7.1 什么算「A 挂了」（允许切）

在 **尚未让 A 接受本单** 的前提下：

| 上游表现 | 切 B | 记入熔断 |
| --- | --- | --- |
| TCP/TLS/DNS 失败、客户端超时且 **未读到任何 HTTP 响应** | 是 | 是 |
| HTTP 502 / 503 / 504 | 是 | 是 |
| 连接建立后超时，但不确定请求是否落地 | **否**（算歧义，见下） | 是（A 标 unknown） |
| 4xx 业务：码无效、已用、余额不足、plan 不对 | **否**（这张 binding 废了；若状态仍是 unused 且确认未核销，可试 B；「已用」则停） | 否 |
| 401 / 403 密钥或白名单 | 否（配置错误，切 B 会掩盖） | 否 |
| 2xx 已接受 / 已返回 `redemption_token` | 否 | 否 |

熔断（复用旧运维设计）：**10 分钟内 3 次** 超时或 5xx → 该账户 **熔断 15 分钟**。熔断中的账户：新兑换跳过它；新双发预检失败（主路径不出货）。半开：15 分钟后允许 1 次探测。

### 7.2 什么绝不能切（防双开）

一旦 A 的 binding 进入 `redeeming` 且已经发出 Redeem，并出现下列任一，**禁止再动 B**：

- A 返回 2xx / `reserved` / `redemption_token`
- A webhook `consumed` / `reserved` / `gpt_direct.completed` / `openai.cdk.consumed`
- A 状态 `reserved` | `consumed` | `unknown`

`unknown` = 请求可能已被 A 吃掉。处理：对用户显示「处理中，请用同一设备查结果」；后台对 A 做 Result 轮询；**B 保持 unused**。人工确认 A 未核销后，才能把 A 标 `failed` 并允许下一次用 B（管理接口，不自动）。

### 7.3 进行中的 A 单

用户刷新、第二标签、Result 轮询：一律跟 **当前 `active_binding_id`**（已选中的那条），不重新选台。

## 8. 状态机

### 8.1 本站行 `cardplatform_cdk_codes`（对外码）

```
issue_status:
  pending ──成功双绑──► active
     │
     └──A 或 B 不可恢复──► failed（不对代理可见）

status（active 之后，沿用现网词）:
  unused ──开始兑──► reserved ──成功──► consumed
                │
                └──业务失败且未核销──► unused（可再兑 / 可切 B）
  unused|reserved ──站长禁用──► disabled
```

另：`fulfilled_account_id` / `fulfilled_provider` 只在 **consumed** 时填写，表示实际履约台。

### 8.2 Binding `site_cdk_bindings.status`

```
unused      已买到上游码，未用于兑换
redeeming   进程内已选定、正在调该台（持有本站行锁时写入）
reserved    该台已接受（token / 上游 reserved）
consumed    该台履约成功
failed      该台明确未核销（4xx 业务或发行失败回滚）
unknown     超时歧义，禁止对兄弟 binding 发 Redeem
retired     兄弟 binding 已 consumed，本条作废（未退款：删除失败或协议不支持）
refunded    已在上游删除且服务费已退回（retired 的理想终态，D2 首选）
disabled    随本站码禁用，或发行回滚时 disable 成功
```

`retired` 与 `refunded` 对外行为完全一样（都禁止再兑），区别只在钱是否收回。运维列表要能筛 `retired`，那是「该退没退回来」的欠账，需要人工去上游补删。

合法转移（实现按表校验）：

| 从 | 到 | 触发 |
| --- | --- | --- |
| unused | redeeming | 路由选中 |
| redeeming | reserved / consumed / failed / unused / unknown | 上游响应 |
| reserved | consumed / failed / unknown | result / webhook |
| unused | retired | 兄弟 consumed（D2） |
| unused / redeeming | disabled | 本站禁用或发行回滚 |
| unused | failed | 发行回滚来不及 disable |

**同一 binding 不得 Redeem 两次。** `reserved|consumed|retired|disabled|unknown` 都不再对该 `remote_code` 发 Redeem。

### 8.3 一张本站码上两条 binding 的联合约束

- 至多一条处于 `redeeming|reserved|consumed|unknown`。
- 出现 `consumed` ⇒ 另一条必须退役：先试删除退款 → `refunded`，删不掉再试 disable → `retired`，两者都失败仍标 `retired` 并告警「B 退役但上游未删除」。**任何情况下都禁止再兑 B**。
- 退款有前置条件：上游「已使用 / 已预留 / 待对账」的卡**不可删除**。所以 B 处于 `unknown`（超时歧义）时不能删，那笔钱要等 A/B 定性后才能回收；`unknown` 的退役必须排队重试，不要当场判失败。
- 两条都 `failed` 且本站仍 unused：本站码作废，走换码/退款流程，不要再自动买第三张绑上来（避免费用失控）。换码是显式动作。

## 9. 前缀与路由入口

### 9.1 本站码格式（推荐）

```
DN-<8 hex>-<8 hex>-<8 hex>
例：DN-A1B2C3D4-E5F60718-90ABCDEF
```

- 前缀 **`DN-`**（Danew），与 `GPTD-` / `SXC-` / `AVF-` 无歧义。
- 不用 `CDK-`（太泛）、不用 `DANEW-`（长、难抄）。
- 24 hex ≈ 96 bit，本站用 `crypto/rand` 生成，`UNIQUE(code)` 兜底碰撞。
- `code_prefix` 存 `DN-` + 前 8 hex（现网列表爱用 14 字符前缀；实现可存 `DN-A1B2C3D4`）。

公开页 placeholder：从 `SXC-XXXX-…` 改为「粘贴卡密（DN- / GPTD- / SXC-）」——只改文案，不改流程。

### 9.2 入口算法（Preview / Preflight / Redeem 共用）

```
normalize(code)
1. 白号 / local_stock → 本地履约，结束
2. 前缀 GPTD-|SXC-|AVF- 或 code_kind=legacy 或无 binding
     → ProviderForLegacy(code)（现网：AVF- 走新协议账户，其余走旧账户）
     → 用户码原样转发
     → 禁止 failover
3. 前缀 DN- 或 code_kind=site
     → 加载 bindings
     → 若 dual_eligible=0（credit* 或降级 A-only）：只试那一条，禁止切
     → 否则按 §11 排序试主、再试备
4. 未落库且不像任何前缀 → 400「卡密格式无法识别」（不要猜测打某一台）
```

未落库的 `DN-`：本站没这行就失败。本站码 **必须先入库再给用户**，不存在「先兑再补登记」。

## 10. 架构

### 10.1 总览

```
公开兑换 / 管理发码 / 代理购卡 / 批量充值 / 代理换码
                    │
                    ▼
           本站履约内核
           订单 · 易支付 · 代理划拨 · 人民币价 · 本站码库存
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
   DualIssuer            RedeemRouter
   （只用于新发）         （legacy 原样 / 本站码换绑）
         │                     │
         │              替换 body.code = remote_code
         └──────────┬──────────┘
                    ▼
              Provider 路由器
         ┌──────────┴──────────┐
         ▼                     ▼
 spacexcard-legacy      avanfinity-2026-08
 /openapi/v1            /api/v1
 X-API-Key              X-App-Id + Secret
 整数 id / GPTD|SXC     UUID cdkId / AVF-
```

三层不许串：adapter 不懂代理；内核看不到 URL；路由器不写人民币。

### 10.2 发码（DualIssue）

```
站长点「购买 1 张 plus」或 fulfillAgentOrder 第 i 张
        │
        ▼
  生成 DN-…（仅内存 + pending 行）
        │
        ├─► AccountA.Issue(plan=plus, qty=1, idem=site-{dn}-acctA)
        │     完整码必须当场返回；空 code = 失败
        │     超时：同键重放（2 分钟窗口）
        │
        ├─► AccountB.Issue(plan=plus, qty=1, idem=site-{dn}-acctB)
        │     同上
        │
        ▼
  两条 binding unused + 本站行 active
        │
        ▼
  返回 / 划拨 / issued_codes 里只有 DN-…
```

### 10.3 兑换快乐路径

```
用户粘贴 DN-A1B2…
  → 锁本站行（BEGIN IMMEDIATE）
  → bindings: A unused primary, B unused
  → 选 A，标 redeeming，提交
  → 把 body.code 换成 A 的 remote_code，调 A.Redeem
  → 2xx + token → A reserved，本站 reserved，active_binding=A
  → 解锁；Result 轮询 A
  → webhook/result 成功 → A consumed，本站 consumed
  → 异步：B unused → retired，Disable B
```

用户始终看到自己的 `DN-`。

### 10.4 兑换 A 挂了切 B

```
锁本站行
  → 选 A，标 redeeming
  → A：DNS/502/连接超时（无 HTTP 体）
  → A 回 unused（或 failed 若确认未接受），记熔断计数
  → 选 B（仍 unused，且 A 不是 reserved/consumed/unknown）
  → B 标 redeeming，body.code = B.remote_code，调 B.Redeem
  → 成功 → 履约台=B；异步退役 A（若 A 仍 unused）
```

```
若 A 已返回 token / reserved：
  → 禁止选 B
  → 只跟 A 的 Result
```

### 10.5 Legacy 兑换

```
用户粘贴 GPTD-xxxx
  → code_kind=legacy 或无 binding
  → 原样 Preview/Redeem 打旧账户
  → 不读 site_cdk_bindings
  → 不熔断切台
```

### 10.6 代理购卡

```
易支付 notify → paid
  → UpdateAgentOrderIssuing
  → for i in 1..N: DualIssue(plan)
  → AssignCDKsToAgent(DN 列表)
  → delivered + order.delivered{ issued_codes: [DN-…] }
```

与现网差异：只是 `issueCDKsForAgentOrder` 换成 DualIssue；webhook 字段名不变。

### 10.7 Webhook（卡台 → 本站）

```
POST /api/v1/webhooks/cardplatform      旧 HMAC(body)
POST /api/v1/webhooks/avanfinity        HMAC(ts + '.' + body)
        │
        ▼
  按账户 secret 验签（禁止混用）
  → 解析 remote_id（旧 cdk_id int / 新 data.object.cdkId UUID）
  → site_cdk_bindings 找 (account_id, remote_id)
       找到 → 更新 binding + 本站行；consumed 则退役兄弟
       找不到 → 再按 legacy upstream_id 更新旧行
       再找不到 → 200 忽略（防探测），只打日志
```

二级 **不**接卡台 webhook。卡台事件只更新本站；代理只收本站 `order.*` / `recharge.*`。

## 11. 兑换路由细节

### 11.1 选 binding 顺序

对 `dual_eligible=1` 的本站码：

1. 过滤：`status IN (unused)` 且账户 `active` 且未熔断。
2. `is_primary=1` 在前，再按 `card_platform_accounts.priority ASC`。
3. 默认：A `is_primary=1`（旧 SpaceX 账户），B 为备。
4. 若主账户熔断：直接从 B 开始（A 仍 unused，未发过 Redeem）。
5. 选中后写入 `active_binding_id`，其它线程只跟这条。

Preview / Preflight / Redeem 必须打 **同一条** binding。Preview 已选定 A 后，Redeem 不得偷偷改 B，除非 Preview 本身就因 A 挂了走了 B，并在 session 里记下。

实现：`cdk_session_bindings` 增加 `binding_id`（可空，legacy 空）。Preview 成功写入；后续步骤用它。

### 11.2 替换转发字段

现网 `PublicCDKRedeem` 把用户 body 原样给 `cli.Redeem`。双绑后：

```
body["code"] = binding.remote_code          // 绝不是 DN-
// redemption_token / credential / device 不动
// 选卡策略 no_auto_card_switch 等仍按本站政策注入
```

Preview 同样：`Preview(ctx, remote_code, device)`。  
Result：token 是上游的，跟当前 binding 的账户走；`result-by-code` 用 **本站码** 查绑定再拿 token。

### 11.3 设备头

新协议要求 `X-Redemption-Device` 为 UUID。本站继续在会话里存 `redemption_device`，对用户只暴露现有 token 流程。切到 B 时：同一设备 UUID 带给 B（B 当新兑换，不是恢复 A 的单）。

### 11.4 批量管理直充（`admin_batch_recharge`）

现网：Issue 1 张原生码再 Redeem。双绑后：DualIssue 得本站码，Redeem 走 RedeemRouter（可切 B）。界面仍不出现卡密（现网已如此）。日志记 `fulfilled_provider`。

## 12. 技术设计

### 12.1 Adapter

现网 `internal/cardplatform.Client` 先当作 `spacexcard-legacy` 皮。handler 改为依赖 `provider.Router`。

```go
type CardProvider interface {
    AccountID() int64
    Protocol() string // spacexcard-legacy | avanfinity-2026-08
    Caps() Caps       // Disable, Offers, ForceNewCard, CreditPlans

    Ping(ctx) error
    Balance(ctx) (*Balance, error)
    SellablePlans(ctx) (*Catalog, error)
    Issue(ctx, IssueReq) (*IssueResult, error) // Code 必填
    ListCDKs(ctx, q) (*CodeList, error)
    Disable(ctx, remoteID string) error        // 无能力则 Caps.Disable=false

    Preview / Preflight / Redeem / Result
    VerifyWebhook(headers, raw) (Event, error)
}

type IssueResult struct {
    RemoteID   string // 旧 int → 十进制字符串；新 = UUID
    Code       string // 完整码，空即失败
    CodePrefix string
    Plan       string
    UnitCents  int64
}
```

禁止 handler 再碰 `int64` 上游 id。`DisableCDK(id int64)` 只留在 legacy adapter 内部。

Avanfinity 要点（旧方案已列，这里只留双绑相关）：

- 鉴权 `X-App-Id` + `X-App-Secret`；公开路径 `/api/public/cdk/*`，result 为 POST。
- generate 响应 + **约 2 分钟**同 `Idempotency-Key` 重放；之后列表 `code=null`，**不能**靠 List/Webhook 补全文。
- `credit*` 的 `Caps.CreditPlans=false`。

### 12.2 发码事务与幂等

对一张本站码：

| 步骤 | 幂等键 | 说明 |
| --- | --- | --- |
| 本站 pending 行 | `code` 唯一 | 崩溃重入：发现 pending 则继续补绑定，不新生成 DN |
| A.Issue | `site-{dn}-a{accountId}` | 窗口内重放拿全文 |
| B.Issue | `site-{dn}-b{accountId}` | 与 A 独立；改 plan 必须换 DN（因而换键） |

代理订单第 i 张：先确定 `DN`（或 pending 行），再套上面的键。**不要**再用单一 `fulfill-{order_no}` 去打两边——一边成功一边重放会把 count/plan 搞乱。旧键只留给 legacy 单台发码。

`forceNewCard` / `preferred_issuer`：按 **该账户** 的现网策略走（旧台选卡偏好，新台账户级 `forceNewCard`）。两边各写各的，不要求同一张物理卡。

完整码硬约束：**Issue 成功 = `remote_code` 已写入 binding。** 超时先同键重放，再换键。换键有双买风险：换键前必须确认旧键没有成功落码（查 binding / 短窗口重放）。落不了全文的成功响应当失败。

### 12.3 `upstream_id INTEGER` 装不下 UUID

现网主键语义靠 `upstream_id INTEGER`。Avanfinity `cdkId` 是 UUID。  
**binding.remote_id TEXT** 存两种：`"1842"` 或 `"550e8400-…"`。  
本站码行：`upstream_id` 改为 **本站局部整数**（见迁移），不再当卡台 id。legacy 行：`upstream_id` 仍是卡台整数，`remote_id` 回填为 `str(upstream_id)`。

白号继续负整数，互不冲突。

### 12.4 禁用

站长禁用一张本站码：

1. 本站 `status=disabled`。
2. 所有 `unused|failed` binding → **优先删除退款**（旧台 `DELETE /cdks/{id}`，未使用的购买码退服务费），标 `refunded`；协议不支持或删除失败再退化为 `Disable(remote_id)` + `disabled`。
3. `redeeming|reserved|unknown`：不盲动上游进行中的单（上游也会拒绝删除已预留的卡），只禁本站新兑换，等终态后再回收。
4. `consumed`：只记本站 disabled 无意义，UI 拒绝「禁用已使用」。

批量禁用同理。新台若无删除/disable path：只改本站+binding，按钮旁注「B 仅本站标记，未退款」。

**禁用一张双绑本站码应该退回两张的钱**（两条 binding 都未使用）。实现时别只删主绑。

### 12.5 可观测

每张本站码记：

- `fulfilled_account_id` / `fulfilled_provider`
- `failover_used`（0/1）
- `failover_reason`（`a_http_503` / `a_timeout` / `a_circuit_open`）

审计：`site_cdk_issue`、`site_cdk_redeem`、`site_cdk_failover`、`site_cdk_retire_spare`。  
日志允许：本站码、账户名、remote_id、remote **prefix**。  
**禁止**日志打完整 `remote_code`（和现网「完整码只在发码响应里」同一级别）。

管理列表「履约台」列读这些字段。用户/代理 API 不返回。

### 12.6 并发（两个标签兑同一张 DN-）

SQLite：`BEGIN IMMEDIATE` 锁本站行（`SELECT … WHERE code=?`）。

1. 已 `consumed` → 直接「已使用」。
2. 已有 `active_binding_id` 且该 binding `redeeming|reserved|unknown` → 不新开路由，跟原单 Result。
3. 否则选 binding、标 `redeeming`、提交、再解锁（HTTP 调用可在锁外，但回来要用行锁写回，并检查没被别人改成 consumed）。

代理批量充值与公开页同时兑：同一把行锁。现网靠 `block_public_redeem` 的部分改由这把锁承担。

### 12.7 2 分钟窗口与进程崩溃

- 崩溃在 A 成功、binding 未写：重入 pending 行，同键打 A，拿到码再写 binding。
- 崩溃在 A 已写、B 未写：只补 B，不重买 A。
- 窗口过了且本地无全文：该 binding 失败，走 D3（整张失败或降级）。不要用 List 幻想补码。

### 13.1 为什么要 binding 表

旧结论「一张码绑一个上游，不必映射表」对 **legacy 透传** 仍成立。  
本稿是 **1 本站码 : 2 上游码**，映射表是正主，不是过度设计。

### 13.2 `card_platform_accounts`

```sql
CREATE TABLE IF NOT EXISTS card_platform_accounts (
```

### 13.3 演进 `cardplatform_cdk_codes`（对外码，含 legacy / 本站 / 白号）

不新建 `site_cdks`，避免拆开 `assigned_agent_user_id`、代理库存、`cdk_session_bindings`。加列：

```sql
ALTER TABLE cardplatform_cdk_codes ADD COLUMN id INTEGER; -- 见迁移：重建表拿真正 PK
ALTER TABLE cardplatform_cdk_codes ADD COLUMN code_kind TEXT NOT NULL DEFAULT 'legacy';
  -- legacy | site | local_stock
ALTER TABLE cardplatform_cdk_codes ADD COLUMN remote_id TEXT NOT NULL DEFAULT '';
  -- 仅 legacy：str(upstream_id)；site/白号空（远程身份在 binding）
ALTER TABLE cardplatform_cdk_codes ADD COLUMN issue_status TEXT NOT NULL DEFAULT 'active';
  -- pending | active | failed
ALTER TABLE cardplatform_cdk_codes ADD COLUMN dual_eligible INTEGER NOT NULL DEFAULT 0;
ALTER TABLE cardplatform_cdk_codes ADD COLUMN fulfilled_account_id INTEGER NOT NULL DEFAULT 0;
ALTER TABLE cardplatform_cdk_codes ADD COLUMN fulfilled_provider TEXT NOT NULL DEFAULT '';
ALTER TABLE cardplatform_cdk_codes ADD COLUMN failover_used INTEGER NOT NULL DEFAULT 0;
ALTER TABLE cardplatform_cdk_codes ADD COLUMN failover_reason TEXT NOT NULL DEFAULT '';
ALTER TABLE cardplatform_cdk_codes ADD COLUMN active_binding_id INTEGER NOT NULL DEFAULT 0;
```

约束：

- `UNIQUE(code)` 已有，本站码/原生码/白号共用，必须全局不撞。
- legacy：`UNIQUE(provider_account, remote_id)` 用 `(code_kind, remote_id)` 不够（多账户）。legacy 继续靠 `upstream_id` 索引；新唯一见 binding 表。
- `code_kind='site'` ⇒ `code` 匹配 `DN-%`。
- `code_kind='legacy'` ⇒ 无 binding 行。
- `code_kind='local_stock'` ⇒ 无 binding，`upstream_id<0`。

`assigned_agent_user_id`、`status`、`plan`、`fee_amount_minor` 含义不变。  
`fee_amount_minor` 对本站码：存 **A+B 成本之和**（管理对账用），代理价仍在订单上。

#### SQLite 重建表拿 `id`（推荐迁移）

现表没有 `INTEGER PRIMARY KEY`。划拨却用 `upstream_id` 更新，本站码会撞车。P1 迁移：

1. 新建 `cardplatform_cdk_codes_new`（`id INTEGER PRIMARY KEY AUTOINCREMENT`，其余列 + 新列）。
2. 拷贝旧行：`code_kind` = `plan='gpt_white'` 则 `local_stock`，否则 `legacy`；`remote_id=CAST(upstream_id AS TEXT)`（负 id 也转）。
3. 换表名，重建索引：`code`、`assigned_agent_user_id`、`code_kind`、`status`。
4. `cardplatform_cdk_notes` 仍按 legacy `upstream_id`；本站码备注改按 `id` 或 `code`（P1 备注可先只支持 code 查询）。

## 14. 路由伪代码

```
func Redeem(siteCode, body):
  BEGIN IMMEDIATE
  row = lock site code
  if row.kind == legacy: COMMIT; return legacyClient.Redeem(userCode, body)
  if row.status in (consumed, disabled): return already_used
  if row.active_binding_id != 0:
      b = load(row.active_binding_id)
      if b.status in (redeeming, reserved, unknown):
          COMMIT; return follow(b)   // Result，不新 Redeem
  candidates = bindings unused, account active, not circuit-open
  sort by is_primary desc, priority asc
  if empty: return all_platforms_unavailable

  chosen = candidates[0]
  chosen.status = redeeming
  row.active_binding_id = chosen.id
  row.status = reserved
  COMMIT

  body.code = chosen.remote_code
  st, raw, err = chosen.Account.Redeem(body)

  BEGIN IMMEDIATE
  if transport_fail_or_5xx(err, st) AND not request_maybe_accepted(err):
      chosen.status = unused
      chosen.last_error = ...
      bumpCircuit(chosen.account)
      row.active_binding_id = 0
      // 尝试下一条 unused（B）
      COMMIT
      return Redeem(...)  // 注意：只循环还 unused 的，且 A 未 unknown
  if ambiguous_timeout:
      chosen.status = unknown
      COMMIT
      return in_progress   // 禁止切 B
  if business_rejected_not_consumed:
      chosen.status = failed
      row.active_binding_id = 0
      COMMIT
      // 若还有 unused 兄弟且 dual_eligible：可再 Redeem 一次
  if accepted:
      chosen.status = reserved
      save token on site code
      COMMIT
  ...

on Fulfilled(chosen):
  chosen.status = consumed
  row.status = consumed
  row.fulfilled_* = chosen
  for sib in other bindings:
      if sib.status == unused:
          sib.status = retired
          async Disable(sib)
```

## 15. Webhook 映射

| 协议 | 验签 | 身份字段 | 本站动作 |
| --- | --- | --- | --- |
| 旧 | `X-Signature` = HMAC(secret, body) | `cdk_id` int | 先 binding，再 legacy `upstream_id` |
| 新 | `X-Avanfinity-Signature: v1=` HMAC(secret, `ts+'.'+body`)，skew≤300s，去重 `X-Avanfinity-Webhook-Id` | `data.object.cdkId` UUID | 只查 binding |

事件：

- `gpt_direct.completed` / `openai.cdk.consumed` → 该 binding `consumed`，本站 `consumed`，退役兄弟
- `reserved` → binding `reserved`（不退役兄弟）
- `released` → 若本站尚未 consumed，binding 回 `unused`，允许再兑（仍先 A 后 B）
- `disabled` / `frozen` → binding `disabled`；若本站还 unused 且双绑还剩一条 unused，**不**自动改本站 disabled（还能兑另一台）；两条都废 → 本站 disabled + 告警
- 未知 `remote_id`：200 + 日志，不创建行

每个账户自己的 `webhook_secret`。新 secret 不从 App-Secret 派生。入口可继续两条 URL，对内收成同一 handler。

## 16. 分期

### P1 —— 双发 + 兑换切台 + 旧码不动（目标可上线）

1. 账户表 + 现网 Key 迁成账户 A；能加账户 B。
2. `CardProvider` 抽出；Avanfinity adapter 能 Issue/Redeem/Webhook。
3. `cardplatform_cdk_codes` 重建加 `id` / `code_kind`；新表 `site_cdk_bindings`。
4. DualIssue：管理发码、`fulfillAgentOrder`、批量直充发码。对外只回 `DN-`。
5. RedeemRouter：legacy 原样；`DN-` 换 `remote_code`；A 不可达切 B；歧义不切。
6. 公开页放行代理名下的 `DN-`。
7. Agent `issued_codes` / 库存 / 划拨只认本站码。
8. Webhook 按 `remote_id` 反查 binding。
9. 禁用本站码 + 两条 binding。
10. **不对 legacy 开 failover。**

验收：

- 旧 `GPTD-` 公开兑仍走旧台，A 宕机旧码就是失败。
- 新发 1 张 plus：库里 1 个 `DN-` + 2 条 binding；代理/用户只见 `DN-`。
- 人工停 A 的 Base：同一张 `DN-` Redeem 打到 B 并成功；用户响应无「B」。
- A 已返回 token 后再停 A：不会出现 B 也被 Redeem。
- 代理购卡 webhook 的 `issued_codes[0]` 以 `DN-` 开头。
- `credit*` 只有 1 条 binding。
- 白号购卡/划拨与现在一致。

### P2 —— 熔断 UI 与成本可见

- 卡台接入页：每账户健康、熔断倒计时、最近错误、余额/库存。
- 开关「允许 A-only 降级出货」（默认关）。
- CDK 列表：绑定列 `A✓ B✓` / `A✓ B✗`、履约台、是否切过。
- 告警：B 连续发码失败、退役 disable 失败、`unknown` 积压。
- `remote_code` 静态加密。

### 明确不做

- 不给 legacy 自动切台、不回填双绑。
- 不把 A/B 码给代理、二级、公开页。
- 不按「兑时再买一台」省钱（和站长方案相反）。
- 不把白号双绑到卡台。
- 不把 `credit*` 打到新台 generate。
- 不为第二套卡台复制发码页/易支付/代理库存。
- 不让二级选台。

## 19. 风险与决策（收口）

| 风险 | 处理 |
| --- | --- |
| **2× 成本** | D1：站内消化 / 涨一张本站码的代理价。UI 让站长看见 A+B 估算 |
| **A 成功 B 未用 = 浪费** | D2：A consumed 后退役+disable B。浪费的是「保险费」，不是双开 |
| **部分双发** | D3：默认整张失败并尽量退 A；降级开关默认关 |
| **进行中双开** | 行锁 + `unknown` 不切 + consumed 后退役兄弟。超时无响应当歧义 |
| **旧码不能切** | 产品如此；文档/客服话术：「旧前缀只在原台」 |
| **上游码泄漏** | 代理/用户/二级/公开 API 永不返回 binding；日志只打 prefix；站长折叠查看需二次点开 |
| **credit* 不能双发** | 单绑旧台；UI 写明无兜底 |
| **白号被误双绑** | `IsLocalStockPlan` 短路，发码入口根本不进 DualIssue |
| **UUID vs INTEGER** | `remote_id TEXT`；本站自己的 `id` 做 PK |
| **2 分钟丢码** | pending 重入 + 同键重放；过窗且无全文 = 失败 |
| **IP 白名单** | A、B 都要填同一出口 IP；一家 403 不当「挂了」去切另一家发码 |
| **现网拦公开兑代理码** | D4：只对 `DN-` 放开 |
| **换键误双买** | 换 Idempotency-Key 前必须确认旧键无成功码 |
| **两边各开一张物理卡** | 接受。本站卖的是「一次成功履约」，不是「同一张卡两备份」 |
