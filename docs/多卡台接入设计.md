# 多卡台接入设计

> **产品决策已更新（2026-08-27）。** 新码的目标模型是「本站统一发码 + 预购 A/B + 兑换切台」，见 **[本站统一发码 · 双卡台绑定设计](本站统一发码-双卡台绑定设计.md)**。
>
> 本文仍是 **协议 / adapter / 账户 / UUID 身份** 的对照底稿。其中「兑换永不换台」「第一期不要同时乱发两家」对 **legacy 原生码（GPTD-/SXC-/AVF-）** 继续成立；**不要**再当成新 `DN-` 本站码的产品结论。旧 P2「发码按优先级兜底选一台」已被双绑预购取代。
>
> 对照现网 SpaceXCard `/openapi/v1` + `X-API-Key`，以及 Avanfinity Developer API `2026-08-01`。  
> 日期：2026-08-27　·　版本：1.1（加指向，正文协议差异未改）  
> 本文只定设计，不改代码。购卡入库回调见 `docs/代理购卡库存同步-对接说明.md`，是另一条线。

---

## 1. 先定三件事

**Avanfinity 不是「再做一套 CDK 站」。** 它和现在接的卡台是同一产品族的新开发者协议：套餐 key 仍是 `plus` / `pro_5x` 这类，业务仍是发码、兑码、余额。不要为它复制发码页、代理库存、易支付、选卡策略。

**本站永远是履约内核，卡台只是供应商。** 代理看到的是本站订单、本站库存、本站人民币价。卡台差异停在 adapter 里。二级系统继续只对接本站（拉单 + `order.delivered`），不要让二级知道后面有几家卡台。

**Legacy 不要「同时乱发两家」。** 旧码还能兑、公开兑换按卡密前缀路由——这期仍要先做到。  
**新本站码相反：生成时就是同时向 A、B 各买一张**（不是乱发，是预绑定）。按套餐分流不再是第二期重点。

## 2. 两套协议真正差在哪

不是换个 Base URL 那么简单。下面这些会直接打到表结构和兑换链路。

| 点 | 现网 SpaceXCard | Avanfinity 2026-08 | 对本站的影响 |
| --- | --- | --- | --- |
| 根路径 | `{site}/openapi/v1` | `{site}/api/v1` | adapter 自己拼，不要写死在 handler |
| 鉴权 | `X-API-Key` | `X-App-Id` + `X-App-Secret` | 凭证模型要从「一把 key」改成「账户 + 协议」 |
| 发码 | `POST /gpt-direct/cdks`，扣套餐费 | `POST /gpt-direct/cdks/generate`，**生成不扣套餐费** | 余额含义变了；不能拿旧「服务费」去理解新报价 |
| 报价 | `GET /gpt-direct/plans`（服务费 + registry） | `GET /gpt-direct/cdk-offers`（美元售价 + **库存** + READY/WAITING_QUOTE） | 可售 = 开关 ∩ 有效价 ∩ 有库存 |
| 可发套餐 | registry 里什么都能发（含点数） | generate 枚举只有 `go / plus / pro_5x / pro_20x` | 点数档必须留在旧台，不能合并成一张「全能价目」 |
| 卡密形态 | 现网码（如 `GPTD-…`），`id` 是整数 | `AVF-` + 32 位 hex，`cdkId` 是 **UUID** | `upstream_id INTEGER` 存不下，必须改身份模型 |
| 完整码窗口 | 发码响应里取 | 成功响应 + **约 2 分钟**同幂等重放，之后列表只有前缀 | 必须当时落库；禁止「先下单再轮询要全文」 |
| 选卡 | `preferred_issuer` / 产品码 | `forceNewCard`：每张码绑一张新卡，失败不换卡 | 现网选卡规则不能原样传过去 |
| 公开兑换 | `/api/v1/cdk/preview|preflight|redeem|result` | `/public/cdk/*`，还要带设备 UUID | 公开 BFF 必须按码路由，不能再打一家 |
| Webhook | `X-Signature = HMAC(body)`，`gpt_direct.*` | `X-Avanfinity-Signature = HMAC(ts + '.' + body)`，`openai.cdk.*` | 两个入站入口，对内收成统一事件 |
| 禁用/解禁 | `/cdks/:id/disable` | 文档里是 `openai.cdk.frozen/disabled` 事件，没有同等路径 | adapter 声明能力；没有的操作 UI 灰掉 |

还有两条硬约束：

1. **写接口要来源 IP 白名单。** 新协议标了 `x-ip-allowlist-required`。现网「出口 IP」卡片要按账户显示，填错白名单会发不出码。
2. **金额是十进制字符串，不是 minor int。** adapter 对内仍转成 cents，避免 handler 里两套算术。

## 3. 目标架构

```
公开兑换 / 代理购卡 / 管理发码 / 批量充值
                 │
                 ▼
        本站履约内核
        （订单、库存、人民币价、代理划拨、易支付）
                 │
        Provider 路由器
        ├─ 发码：legacy / credit* 仍选一台；新本站码 DualIssue A+B（见绑定设计）
        └─ 兑换：legacy 按前缀；DN- 按 binding，A 挂了才用 B
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
 spacexcard-legacy      avanfinity-2026-08
 /openapi/v1            /api/v1
 X-API-Key              X-App-Id + Secret
```

三层，不许串层：

| 层 | 干什么 | 不干什么 |
| --- | --- | --- |
| Provider adapter | HTTP、鉴权、路径、验签、把上游 JSON 收成内部结构 | 不知道代理、易支付、人民币 |
| 路由器 | 发码选哪家账户；兑换按码前缀找账户 | 不写死 URL |
| 履约内核 | 现有 `fulfillAgentOrder`、公开 BFF、代理库存 | 不再 `cardplatform.NewFromSettings()` |

建议的内部接口（名字可再磨，形状不要再膨胀）：

```go
type CardProvider interface {
    ID() string
    Protocol() string          // spacexcard-legacy | avanfinity-2026-08
    Capabilities() Caps        // 能否 disable、有无选卡、有无 offers

    GetBalance(ctx) (*Balance, error)
    GetCatalog(ctx) (*Catalog, error)          // 统一成「可售档位」
    Issue(ctx, IssueReq) (*IssueResult, error) // 必须带回完整码
    ListCodes(ctx, ListQuery) (*CodeList, error)

    Preview / Preflight / Redeem / Result      // 公开兑换
    VerifyWebhook(headers, raw) (Event, error)
}
```

`IssueResult` 对内统一：

- `ExternalID string`（旧台用数字转字符串，新台用 UUID）
- `Code` / `CodePrefix` / `Plan`
- `UnitPriceCents`（新台从 `salePrice` 折算；旧台从服务费折算）

禁止 handler 再碰 `int64` 上游 ID。

## 4. 数据怎么改

现在所有码挤在 `cardplatform_cdk_codes.upstream_id INTEGER`。Avanfinity 的 `cdkId` 是 UUID，这条路走到头了。

**身份改成「账户 + 外部 ID 字符串」。**

```
card_accounts
  id, name, protocol, site_base
  cred_public          -- app_id 或空
  cred_secret          -- 加密后的 key / app_secret
  webhook_secret
  status               -- active / disabled
  is_default_issuer    -- 新发码默认走谁
  created_at

cardplatform_cdk_codes  （演进，不是新表）
  provider             -- 账户 id 或协议名，第一期用账户 id
  external_id          -- TEXT，唯一 (provider, external_id)
  upstream_id          -- 旧整数，仅兼容；新码写 0
  code, code_prefix, plan, status, assigned_agent_user_id
```

路由规则：

- **发码（legacy / credit*）**：看 `is_default_issuer`（通常旧台）。
- **发码（新本站码 plus/pro/go）**：DualIssue，A+B 各一张，见绑定设计。不再做 `plan_routing` 选一台。
- **兑换 / 查单 / 禁用（legacy 原生码）**：先用本站已存的 `provider`；公开兑换还没落库时，用前缀：
  - `AVF-` → Avanfinity 账户
  - `GPTD-` / `SXC-` → 默认旧台
  - **不 failover**
- **兑换（`DN-` 本站码）**：读 `site_cdk_bindings`，转发 **绑定的上游码**；A 不可达且未核销才用 B。
- **Webhook**：打到对应账户的入口，用该账户的 secret 验签，再按 `remote_id` 更新 binding 或 legacy 行。

旧数据迁移：已有行 `provider = 旧账户`，`external_id = str(upstream_id)`。读路径两周内两列都认。

`agent_orders`、`admin_recharge_items` 增加 `provider` / `external_id`，对账才不会串台。

## 5. 目录、库存、钱

两家的「价」不是同一个东西。

| | 旧台 `plans` | 新台 `cdk-offers` |
| --- | --- | --- |
| 价 | 卡台服务费（USD minor） | CDK 美元售价 `salePrice` |
| 能不能卖 | `enabled` ∩ registry | `enabled && pricingStatus=READY && salePrice != null && stock > 0` |
| 点数档 | 有 | generate **没有** |

本站对外（代理门户、管理发码）继续用**逻辑套餐 key**（`plus`）。  
内部 catalog 每一行带：

- `key` / `label`
- `providers[]`：谁能发这个档
- `stock`：新台有、旧台没有就标未知
- `upstream_usd_cents`：只给运营看成本，不自动改代理人民币价

**代理人民币价仍是本站 `agent_plan_fees`。** 不要把 Avanfinity 的 `salePrice` 同步进售价，否则汇率和加价会被上游报价带着跑。运营在「代理管理」里自己定 CNY；卡台接入页只展示上游成本和库存，方便决定默认发码源。

点数（`credit250` 等）第一期：**只允许旧台发。** 新台选点数直接拒，文案写清。

## 6. 发码与兑换

### 发码

`fulfillAgentOrder` / 管理发码 / 批量自动发码 都走 `Issuer.Issue()`。

Avanfinity adapter：

- `POST /gpt-direct/cdks/generate`，`quantity` + `Idempotency-Key`
- 响应里立刻抽出 `items[].code`，**缺码就当失败**，不要入库半截
- 幂等键继续用现有 `fulfill-{order_no}`；改 `plan` / `quantity` / `forceNewCard` 必须换新键（上游规定）
- 第一期 `forceNewCard` 做成账户级开关，不要复用现网产品码选卡

旧台 adapter：保持现在的 `POST /gpt-direct/cdks` + 选卡偏好。

### 兑换

公开 BFF 不再写死 `PublicCDKBase()`。

```
preview(code)
  → DN- / code_kind=site：用 binding.remote_code 打对应账户（可切未核销的备绑）
  → 本站能查到 legacy 码？用该码的 provider（不切台）
  → 否则 prefix：AVF- 走新台，其它走旧台
  → 打对应 Preview
```

设备 UUID：新台要求同一设备后续步骤带同一个 UUID。本站在 `cdk_session_bindings` 里存 `redemption_device`，对用户仍然只暴露现有 token 流程。

Webhook：

| 入口 | 验签 | 对内 |
| --- | --- | --- |
| `/api/v1/webhooks/cardplatform` | 旧 HMAC(body) | `code.consumed` 等 |
| `/api/v1/webhooks/avanfinity` | HMAC(ts + '.' + body) | 同一套内部事件 |

`openai.cdk.consumed` → 本地 `consumed`。不要让二级去接卡台 webhook。

## 7. 后台怎么摆

还是「卡台接入」一页，不要「卡台接入 2」。

```
卡台接入
├─ 账户卡片列表（名称 / 协议 / 默认发码 / 连通 / 余额）
├─ 点开一张：
│    协议（旧 OpenAPI / Avanfinity 2026-08）
│    站点根地址
│    凭证（Key 或 App-Id + Secret）
│    Webhook URL（按协议展示不同路径）
│    出口 IP（填到该账户白名单）
│    上游报价与库存（只读）
│    「测连通 / 拉报价 / 测发 1 张」（测发码写进本站库存并标测试）
└─ 默认发码源（单选）

代理管理        人民币价、易支付、二级回调 —— 与卡台无关
CDK 卡密        列表加「来源」列（账户名），筛选按账户
兑换对账        上游订单仍按账户去拉，禁止混打
```

代理门户、公开兑换页**不出现卡台名字**。用户只看到套餐和卡密。

## 8. 能力矩阵（第一期谁做什么）

| 能力 | 旧台 | 新台第一期 | 做不到时 |
| --- | --- | --- | --- |
| 发 plus / pro_5x / pro_20x / go | 要 | 要 | — |
| 发点数档 | 要 | 不做 | UI 禁用 + 接口拒 |
| 选卡 / 产品偏好 | 要 | 用 `forceNewCard` 开关代替 | 选卡配置对新能源灰 |
| 禁用 / 解禁码 | 要 | 若无对等 API 就只改本站状态 | 按钮旁注「仅本站标记」 |
| 公开兑换 | 要 | 要（前缀路由） | — |
| 余额 | 要 | 要 | — |
| 上游库存 | 无 | 展示，发码前可预检 | 旧台不展示库存 |

## 9. 明确不做

- 不为 Avanfinity 新开导航、新开代理库存、新开易支付。
- 不在主站做「替二级同步库存」的定时任务（见购卡对接文档）。
- 不靠 `GET /gpt-direct/cdks` 把完整码补回来——补不回来。
- 不把两家报价平均成一个「官方价」给代理。
- P1 对 **legacy 原生码** 不做自动故障转移。已发出的 GPTD-/SXC-/AVF-、进行中的旧兑换、旧 webhook **永远不换台**。
- **新本站码** 的兑换 failover 是绑定设计的 P1，不是「发码选另一台」。
- 不让二级选卡台。二级只认本站 `order_no` 和 `issued_codes`（落地后为 `DN-`）。

## 10. 落地顺序

**P0（已另文，和卡台无关）**  
购卡 `order.delivered` 回调 + 二级拉单兜底。多卡台做完，这条仍然成立。

**P1 — 能接进第二家，旧业务不炸**

1. 抽出 `CardProvider`，现网 client 做成 `spacexcard-legacy`，所有 `NewFromSettings()` 改为 `DefaultIssuer()` / `ProviderForCode()`。
2. 表加 `provider` + `external_id`，旧数据回填。
3. 实现 `avanfinity-2026-08`：鉴权、balance、offers、generate、公开兑换、独立 webhook。
4. 卡台接入页改成「至少两张账户卡」：旧账户迁移现有 `card_api_*`，新账户填 App-Id/Secret。
5. 公开兑换按前缀路由。管理发码可选账户，默认 `is_default_issuer`。

验收：旧码照兑；从新台发 1 张 `AVF-` 码，公开兑换走新路径成功；代理购卡仍只看到本站订单。

**P2 — 熔断 UI（发码兜底已被双绑取代）**

旧设想 `IssueWithFailover`（按优先级试一台）**不再做**。改见 [本站统一发码 · 双卡台绑定设计](本站统一发码-双卡台绑定设计.md) 的 DualIssue + RedeemRouter。

P2 只补：账户健康 / 熔断倒计时 / 绑定列 / 降级开关。`credit*` 仍只走旧台。Legacy 兑换仍按码前缀，不切台。

**P3 — 以后真有第三家无关卡台**

再加一个 adapter 包。表不用再迁。前提是它也能：同步返回完整码、有可路由的码前缀、有可验签的 webhook 或可轮询的订单。

## 11. 风险

1. **UUID vs INTEGER**：不改身份就接新台，必炸。P1 第一刀就是这个。
2. **码窗口 2 分钟**：进程在落库前崩溃，码回不来。`Issue` 要先落库再返回；幂等重放窗口内可再打一次上游要码。
3. **公开兑换打错台**：`AVF-` 打到旧 `/api/v1/cdk` 会直接 404。前缀路由是 P1 必做，不是优化。
4. **IP 白名单**：新账户出网 IP 没进白名单，表现是发码 403，不像「没配 key」。
5. **目录分裂**：运营以为新台也能发点数。UI 必须按账户显示「能发哪些档」。
6. **测试发码**：点「测发 1 张」会真实出码。要写进库存并标测试，避免当正常货卖掉。

## 13. 和「二级库存同步」的关系

多卡台解决的是：**本站向哪家上游要码。**  
二级库存同步解决的是：**本站发货后怎么告诉二级。**

新台接好了，`fulfillAgentOrder` 仍然是：要码 → 划给代理 → `order.delivered`。二级文档不用改。不要把卡台 webhook 暴露给二级。
