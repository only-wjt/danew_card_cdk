# 代理购卡库存同步 · 主站 / 二级对接说明

> 给二级代理系统的对接契约。主站 = 本 CDK 站；二级 = 你们自己的进货 / 库存系统。  
> 日期：2026-08-27　·　文档版本：1.0　·　主站 API 前缀：`/api/v1`
>
> 多卡台目标模型见 [本站统一发码 · 双卡台绑定设计](本站统一发码-双卡台绑定设计.md)。落地后 `issued_codes` / `GET /agent/cdks` 里的码是本站 `DN-` 前缀，字段名和入库方式不变；不要依赖 `GPTD-` 前缀当路由。

---

## 0. 先看结论

| 问题 | 结论 |
| --- | --- |
| 二级下单后库存不自动入库 | 主站发货后会推 `order.delivered`。充值回调（`recharge.*`）覆盖不了购卡。 |
| 二级现在能不能自己入库 | **能。** 拉单接口已上线，不必等主站发版。 |
| 正确做法 | **主路径：主站推 `order.delivered`。兜底：二级每 30–60 秒拉已发货订单。** |
| 主站会不会替二级扫库存 | **不会。** 库存所有权在二级。主站只保证：发货落库、能拉到码、能推到你们的 URL。 |
| 易支付 notify 丢失 | 主站自己查单补履约，二级不用管。没发货之前拉单也看不到码。 |

**分工**

| 事项 | 状态 | 谁做 |
| --- | --- | --- |
| `GET /agent/orders` 拉单（含完整卡密） | **已上线** | 二级现在就能接 |
| `GET /agent/cdks` 对账补漏 | **已上线** | 二级现在就能接 |
| Webhook `order.delivered` / `order.fulfill_failed` | **主站已入队** | 二级实现接收；未配回调则只靠拉单 |
| 易支付查单补履约 | 主站内部 | 二级无事 |

建议二级：**先上拉单，再接回调。** 回调上线后拉单不要删，只把间隔放宽。

## 1. 鉴权与基地址

所有开放接口：

```
Authorization: Bearer ak_live_xxxxxxxxxxxx
```

API Key 在代理门户「API 密钥」页创建，只展示一次。

基地址 = 主站对外根地址 + `/api/v1`，例如：

```
https://<主站域名>/api/v1/agent/orders
```

门户登录 cookie **不能**当二级服务端凭证。必须用 API Key。

---

## 2. 订单状态（只认这些）

购卡订单号一律以 `AG` 开头。待支付 30 分钟后过期。

| status | 含义 | 二级要不要入库 |
| --- | --- | --- |
| `pending_pay` | 待支付 | 否 |
| `paid` | 已支付，即将发货 | 否 |
| `issuing` | 正在向卡台要码 | 否 |
| `delivered` | 已发齐并划到代理名下 | **是，按 `order_no` 入库** |
| `paid_undelivered` | 已付款但发货失败/不齐 | 否（可告警）；`issued_codes` 里若有码，可先入库未齐部分 |
| `expired` | 超时未付 | 否 |
| `cancelled` | 已取消 | 否 |

入库主键用 **`order_no`**，不要用卡密当订单主键。同一张码只属于一个 `order_no`。

## 3. 拉单兜底（已上线，二级现在做）

支付完成后，主站会发码并把码划到该代理。码出现在订单详情和「我的卡密」里。  
二级不需要等回调，按下面做即可自动入库。

### 3.1 推荐：扫已发货订单

间隔 **30–60 秒**（不要低于 15 秒）。只拉已发货：

```http
GET /api/v1/agent/orders?status=delivered&page=1&page_size=50
Authorization: Bearer ak_live_...
```

响应：

```json
{
  "list": [
    {
      "order_no": "AG1724736000a1b2c3d4",
      "plan": "pro_5x",
      "plan_label": "Pro 5x",
      "count": 2,
      "status": "delivered",
      "issued_count": 2,
      "issued_codes": ["GPTD-AAAA-BBBB-CCCC", "GPTD-DDDD-EEEE-FFFF"],
      "paid_at": "2026-08-27 17:01:02",
      "delivered_at": "2026-08-27 17:01:08",
      "created_at": "2026-08-27 17:00:10",
      "updated_at": "2026-08-27 17:01:08"
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 50
}
```

入库规则：

1. 本地已有该 `order_no` 且已入库 → 跳过。
2. `status === "delivered"` 且 `issued_codes.length >= count` → 整单入库。
3. 以 `issued_codes[]` 为准，不要自己拼码。

单条详情（支付回跳后立刻查这一单）：

```http
GET /api/v1/agent/orders/{order_no}
```

支付回跳只表示用户回来了，**不表示已发货**。请一直查到 `delivered` 或 `paid_undelivered`。

### 3.2 补漏：对库存

怀疑漏单时：

```http
GET /api/v1/agent/cdks?status=unused&page=1&page_size=200
```

```json
{
  "list": [
    {
      "code": "GPTD-AAAA-BBBB-CCCC",
      "code_prefix": "GPTD-AAAA-BB",
      "plan": "pro_5x",
      "status": "unused",
      "created_at": "2026-08-27 17:01:08"
    }
  ],
  "total": 1,
  "summary": { "total": 1, "unused": 1, "reserved": 0, "consumed": 0 }
}
```

本地没有的 `code` 补进库存。这是对账，不是主路径。

### 3.3 下单（若二级代下）

```http
POST /api/v1/agent/orders
Content-Type: application/json

{ "plan": "pro_5x", "count": 2, "pay_type": "alipay" }
```

```json
{
  "order": { "order_no": "AG...", "status": "pending_pay" },
  "pay_url": "https://..."
}
```

把用户带到 `pay_url`。回来后用 `GET /agent/orders/{order_no}` 等到 `delivered`，或走第 3.1 节扫描。

继续支付：`POST /api/v1/agent/orders/{order_no}/repay`（不会新开单）。

## 4. 回调主路径（主站已入队）

购卡发货现在会入队下面两个事件。验签、重试、投递日志与现网充值回调相同。代理需在门户配置 URL 和 Secret，否则事件不会投递（拉单兜底仍可用）。

### 4.1 配置

代理门户 → 设置：

1. 填 `Webhook URL`（公网 `https`，不要内网 / `127.0.0.1` / 云元数据地址）。
2. 点「轮换 Webhook Secret」，密钥只显示一次。没有 Secret 主站不会投递。

同一个 URL 同时收充值和购卡事件，用请求头 `X-Webhook-Event` 分支。

### 4.2 请求

```
POST {你们的 Webhook URL}
Content-Type: application/json
User-Agent: danew-agent-webhook/1
X-Webhook-Id: evt_AG1724736000a1b2c3d4_delivered
X-Webhook-Event: order.delivered
X-Webhook-Timestamp: 1756280468
X-Signature: <hex>
```

`X-Signature` = `hex(HMAC-SHA256(secret, timestamp + "." + rawBody))`  
必须用**原始 body 字节**验签，不要先 JSON 再序列化。  
建议拒绝 `|now - timestamp| > 300` 秒的请求。

Node：

```javascript
const crypto = require("crypto");
function verify(rawBody, timestamp, signature, secret) {
  const expect = crypto.createHmac("sha256", secret)
    .update(timestamp + ".")
    .update(rawBody)
    .digest("hex");
  return expect.length === signature.length &&
    crypto.timingSafeEqual(Buffer.from(expect), Buffer.from(signature));
}
```

Python：

```python
import hmac, hashlib
def verify(raw_body: bytes, timestamp: str, signature: str, secret: str) -> bool:
    expect = hmac.new(secret.encode(), timestamp.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expect, signature)
```

收到后 **5 秒内返回 2xx**。非 2xx / 超时 10 秒会重试：30s → 2min → 10min → 30min → 2h，共 6 次。  
同一 `event_id` 可能投多次，按 `X-Webhook-Id` / `event_id` 幂等。

### 4.3 `order.delivered`（入库）

`event_id` 稳定为 `evt_{order_no}_delivered`，同一单只成功入队一次。

```json
{
  "event_id": "evt_AG1724736000a1b2c3d4_delivered",
  "event_type": "order.delivered",
  "created_at": "2026-08-27T09:01:08Z",
  "data": {
    "order_no": "AG1724736000a1b2c3d4",
    "plan": "pro_5x",
    "plan_label": "Pro 5x",
    "count": 2,
    "issued_count": 2,
    "issued_codes": ["GPTD-AAAA-BBBB-CCCC", "GPTD-DDDD-EEEE-FFFF"],
    "delivered_at": "2026-08-27 17:01:08"
  }
}
```

处理：验签 → 按 `event_id` 去重 → 按 `order_no` 写入库存 → 2xx。  
不要先回 2xx 再异步入库；失败请回 5xx，主站会重试。

### 4.4 `order.fulfill_failed`（告警，默认不入库）

已付款但卡台发码失败或不齐。`event_id` 为 `evt_{order_no}_fulfill_failed`（同一单多次失败只通知一次）。之后若发货成功，仍会再推 `order.delivered`。

```json
{
  "event_id": "evt_AG1724736000a1b2c3d4_fulfill_failed",
  "event_type": "order.fulfill_failed",
  "created_at": "2026-08-27T09:01:20Z",
  "data": {
    "order_no": "AG1724736000a1b2c3d4",
    "plan": "pro_5x",
    "plan_label": "Pro 5x",
    "count": 2,
    "issued_count": 0,
    "issued_codes": [],
    "fail_reason": "卡台未返回完整卡密"
  }
}
```

`issued_count > 0` 时表示发出一部分。这些码已在主站代理库存里，二级可以先收，等 `delivered` 再按 `order_no` 补齐。

### 4.5 和现网充值事件的关系

| event_type | 现在有没有 | 用途 |
| --- | --- | --- |
| `recharge.completed` / `failed` / `unknown` | 有 | 代客充值终态，**不是进货** |
| `batch.completed` | 有 | 代客批量充值汇总 |
| `order.delivered` | 已入队 | 购卡到货，**这才是入库** |
| `order.fulfill_failed` | 已入队 | 购卡发货失败 |

不要把 `recharge.completed` 当成进货成功。

## 5. 二级最小实现

```
支付回跳或定时器
        │
        ▼
GET /agent/orders/{order_no}  或  GET /agent/orders?status=delivered
        │
        ├─ delivered 且本地无此 order_no → 把 issued_codes 写入库存
        ├─ paid / issuing → 过几秒再查
        ├─ paid_undelivered → 告警，不要当整单成功
        └─ pending_pay → 继续等（或提示去支付）

（主站发版后并行）
Webhook POST
        │
        ├─ 验签失败 → 401
        ├─ order.delivered → 与拉单同一套入库函数（按 order_no 幂等）
        ├─ order.fulfill_failed → 告警
        └─ recharge.* / batch.completed → 走你们原来的充值逻辑
```

伪代码：

```ts
async function importIfNew(order: { order_no: string; status: string; issued_codes?: string[] }) {
  if (order.status !== "delivered") return;
  if (await db.hasPurchase(order.order_no)) return;
  await db.insertCodes(order.order_no, order.issued_codes ?? []);
}

// 兜底
setInterval(async () => {
  const { list } = await get("/agent/orders?status=delivered&page_size=50");
  for (const o of list) await importIfNew(o);
}, 45_000);

// 回调（主站发版后）
app.post("/webhook/agent", rawJson, (req, res) => {
  if (!verify(req.rawBody, req.get("X-Webhook-Timestamp"), req.get("X-Signature"), SECRET)) {
    return res.status(401).end();
  }
  const evt = JSON.parse(req.rawBody);
  if (evt.event_type === "order.delivered") {
    importIfNew({ ...evt.data, status: "delivered" });
  }
  res.status(200).json({ ok: true });
});
```

## 6. 主站明确不做的事

- 不替二级跑「进货单同步」定时任务。
- 不在回调里只推「已发货」而不带码——`order.delivered` 会带 `issued_codes`。
- 不保证用户支付回跳时已经发完货；回跳只表示浏览器回来了。
- 完整卡密只出现在：订单详情、`GET /agent/cdks`、以及 `order.delivered`。列表接口的 `code_prefix` 不能当兑换码。

易支付异步通知可能被 Cloudflare / 境外网络丢掉。主站会另做查单：发现已支付就执行原来的发货。二级始终只看 `delivered` / 回调，不要自己去查易支付。
